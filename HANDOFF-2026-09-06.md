### Correction to finding 6 — it was wrong in an important way

The finding said "Check for Updates errors for every 1.10.0 Direct user". Measured instead:
`https://distavo.com/appcast.xml` returned **200 and was validly signed, but advertised 1.8.0**.
The feed was never broken — it was **stale**, so Sparkle told every Direct user *"you're up to
date"* while 1.9.x and 1.10.0 existed. A silent wrong answer, harder to notice than an error.

Root cause was as described: `release.yml` only *attaches* `appcast.xml` to the GitHub Release,
there is no site-deploy workflow, so publishing was a manual step done once for 1.8.0 and never
again.

- Added **`ops/publish-appcast.sh`** — refuses an appcast that doesn't name the tag or carries no
  `edSignature`, backs up the live file, uploads, verifies the published URL. `DRY_RUN=1` checks
  without uploading.
- **Published for real** (Marc approved): live feed now serves 1.10.0, previous feed backed up
  server-side as `appcast.xml.bak-2026-09-06`.
- The live `appcast.xml` is root-owned, so a straight `scp` onto it fails. The script uploads
  beside the target and `mv`s into place — unlink/rename needs *directory* permission, not file
  permission, and the rename is atomic so nginx can't serve a half-written feed (`33af6d1`).
- Corrected `docs/distribution-checklist.md` 2.7 and `docs/update-verification.md`, which both
  still claimed `SUPublicEDKey` was empty and Sparkle refused updates — untrue since 1.8.0.

**This is now a required manual step after every Direct release.** Run
`./ops/publish-appcast.sh vX.Y.Z`.

## 4. UI-health findings from the walkthrough (all three closed)

- **#1829 → `afceff8`** — `hasLastNote` never seeded from disk, so both menu items were greyed out
  after every relaunch. Added `DistavoState.newestNote(inNotesDir:)` and seeded at launch and on
  `applyConfig`. **Also split `hasLastTranscript` out**: the note lives in `notesDir` but its
  transcript lives in the *work* dir, so one shared flag would have enabled "Copy last transcript"
  with nothing to copy — trading one wrong state for another.
- **#1828 → `2edd565`** — WhisperKit *stringifies* the URLError into its own "Model not found,
  check the repo name" message, so a typed `as? URLError` cast would never catch it.
  `NetworkScope.describesOfflineFailure` casts first, then falls back to text matching. Negative
  tests assert unrelated failures are **not** reported as offline.
- **#1827 → `52a8023`** — added `failedBases()` and a persistent menu line +
  "Retry N failed recordings". `lastError` only ever showed the current run, which is why two
  recordings sat unnoticed for five weeks. **Marc's two 2026-07-07 files were deliberately not
  touched** — 4 KB near-empty WAVs (a failed *capture*), his data to delete or re-record. They will
  now show up in the menu.

Note #1827 and review finding 3 are **complementary, not duplicates** (Vikunja #1878 guessed they
were the same): finding 3 is the transient case that should never have failed; #1827 is the
permanent case that will always exist and now has to be visible.
